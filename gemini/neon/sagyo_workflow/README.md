# 作業記録の使い方

## 目的

このフォルダーには、会話アーカイブの作成結果だけでなく、対象を特定した根拠、収録方法、判断、コミットの進み方、再開手順を残します。環境が失われても、リモートの状態記録から次の作業を再開できるようにします。

## この記録の構成

- [進捗ログ](progress.md) — 確認、作成、修正、コミットを時系列で記録。
- [判断記録](decisions.md) — 保存先、対象範囲、Markdown再構成などの理由。
- [再開用の状態](state.md) — 対象ファイル、件数、最新チェックポイント、残作業。
- [会話記録テンプレート](conversation-template.md) — 次の会話を同じ基準で整理する雛形。

## 今回の長文会話の記録方法

1. GitHubのリポジトリ、既定ブランチ、保存先ディレクトリ、既存ファイルの内容とblob SHAを読み、作成・更新・削除を区別する。
2. クラウドブラウザーで開いているタブとGemini画面の会話名を照合する。今回の対象は既存スレッド「トポス創発法」だった。
3. ブラウザー画面を先頭から末尾まで選択してコピーし、ローカルの退避テキストとして保存する。これは復旧用の作業ファイルで、サイドバー等も含むためリポジトリへは載せない。
4. 会話本文は発言ごとに整理する。画面上のユーザープロンプト見出しとGemini回答領域の数が一致するかを数え、先頭と末尾の発言を照合して、途中で切れていないことを確かめる。今回確認できたのはユーザー48件・Gemini回答48件、計48往復・96発言だった。以前の9往復という記録は不完全だったため、全件版へ置き換えた。
5. タイトルをファイル名に使い、順番を保ってMarkdownへ再構成する。話者見出し、本文中の見出し、段落、リスト、表、コードフェンス、数式を整える。会話外のUI、サイドバー、セッションURLやIDは本文に含めない。
6. 会話本文とブラウザー操作・判断の記録を分ける。原文は基本的に維持し、数式記号や空白を読みやすく整えた場合は、その限界を作業記録に記す。
7. 完成した会話ファイルを先にリモートへコミットする。続けて一覧README、進捗、判断、状態、テンプレートを小さなまとまりごとに更新し、各成功コミットSHAを記録する。
8. GitHubから保存後のファイルを読み戻す。タイトル、先頭と末尾、発言数、リンク先の存在、セッションURLが含まれていないことを確認し、最後に状態ファイルを更新する。

## 再開とチェックポイント

GitHubのContents APIによる各作成・更新・削除は、その操作ごとに対象ブランチへコミットを作ります。成功応答のcommit SHAを次の作業記録へ引き継ぎます。作業中に環境が消えたら、まず `state.md`、次に `progress.md` と `decisions.md` を読み、GitHubのmain先端と各ファイルの現状・blob SHAを読み直します。すでにコミット済みの作業は繰り返さず、残作業だけを続けます。

新規作成が失敗した場合は同じ操作をすぐ繰り返さず、対象パスが存在するかを確認します。既存ファイルの更新・削除では、必ず最新blob SHAを使います。古いファイル名をタイトル名へ移すときは、新ファイルの作成とREADMEのリンク更新を先に済ませ、その後に旧版を削除します。

## 次回に活かすヒント

- 長い会話では、最初に表示件数だけで全体を判断しない。発言見出しの総数と最後の発言まで照合する。
- コピーした全文の先頭・末尾を会話画面と照合し、欠落・重複を確認してから投稿する。
- コピー用の生テキストに会話外の情報が混ざる場合がある。会話本文だけを分離し、作業用の退避データは公開対象にしない。
- 会話名をファイル名にし、READMEから辿れるようにする。
- GitHubでMarkdownを開いたときにチャットの読み順が伝わるよう、話者と往復を明示する。色、余白、操作ボタン、アニメーションはMarkdownでは再現できないため、文章構造を優先する。
- アクセシビリティ表示から再構成する数式や表記は画面上の空白と一致しない場合がある。判読できない箇所を推測で補わず、必要なら記録に制約を明記する。
- 対象を取り違えた場合は、正しい本文に差し替え、古い案内や件数も全て直す。誤りと訂正の経緯は履歴として残し、現行手順には古い件数を残さない。
- 小さなコミットを積み上げ、各コミット後に再開できる状態を保つ。

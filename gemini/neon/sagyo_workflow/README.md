# 作業記録の使い方

## 目的
このフォルダーは、会話を保存した結果だけでなく、判断の理由・進み方・次回の再開点も残すための作業ノートです。環境が切れても、状態ファイルから次の作業を特定できるようにします。

## この記録の構成

- [進捗ログ](progress.md) — 確認、作成、更新、コミットを時系列に記録。
- [判断記録](decisions.md) — パスの解釈、会話の収録範囲、表示方針など、後で見直したい選択を記録。
- [再開用の状態](state.md) — ブランチ、基点・最新コミット、完了項目、残作業をまとめる。
- [会話記録テンプレート](conversation-template.md) — 次の会話アーカイブを作るときのひな形。

## 今回の作業手順

1. リポジトリの権限、既定ブランチ、指定パスを読み取り専用で調べる。
2. 既存ファイルの内容を読み、作成と更新を区別する。空ファイルも既存ファイルとして扱う。
3. 最初に状態ファイルを作り、対象、基点コミット、未完了項目、復旧方法を書く。
4. 可視の会話メッセージを順番どおりに記録する。ユーザーの原文は直さず、作業者の解釈は別のログに置く。
5. 会話本文は GitHub Flavored Markdown で話者見出し、引用ブロック、連番、区切り線を使って整える。
6. ブラウザーで確認したことや、何を操作したかは会話本文に混ぜず、進捗ログに分ける。
7. ひとまとまりの成果ごとにコミットし、コミット SHA と残作業を進捗・状態に反映する。
8. GitHub からファイルと最新コミットを読み直し、リンク、内容、保存先を確認する。

## コミットと再開

GitHub のファイル作成・更新 API は、指定ブランチにコミットを作ってリモートへ反映します。この作業ではローカル clone を前提にせず、各更新の成功結果にある commit SHA をチェックポイントとして残します。新規作成が失敗した場合は同じ操作を繰り返さず、対象パスが存在するかを調べ、必要なら最新 blob SHA を取得して更新します。

中断後は `state.md` → `progress.md` → `decisions.md` の順で読みます。次に GitHub 上で最新のブランチ先端と該当ファイルを確認し、チェック済み項目と重複しないよう未完了の作業だけを続けます。

## 次回に活かすヒント

- 会話記録と作業記録を分けると、原文と後からの説明が混ざりません。
- 時刻や UI の装飾が実際に確認できないときは作り足さず、記録日と表示上の制約を注記します。
- 長い会話は、会話 ID や話題ごとにファイルを分け、一覧 README から辿れるようにします。
- 既存 README が空でも上書き前に内容と blob SHA を読みます。
- コミットは細かくても、状態ファイルには直近の成功 SHA と次の具体的な作業を書き、復旧の手がかりを保ちます。
- 画面上の文章は原文で保存し、要約・翻訳・用語統一は別の欄に分けると、後の検証が容易です。

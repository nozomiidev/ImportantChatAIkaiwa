# 判断記録

## 1. 保存先はディレクトリ、ブランチは main
依頼文の `gemini/neon の下に` は、リポジトリ内の保存先パスと解釈した。最初の進捗文ではブランチ名と取り違えたが、ブランチ検索で `gemini/neon` が見つからず、リポジトリの `gemini/` 配下に既に `neon/` ディレクトリがあることを確認したため訂正した。作業開始時の既定ブランチは `main` で、指定した main へのコミット・プッシュはユーザーの依頼に含まれていた。新しいブランチは作成していない。

## 2. 会話記録と作業ログを分離
ユーザーとアシスタントの文章を `conversation.md` に、ページ状態・GitHub 操作・判断・復旧手順を `sagyo_workflow/` に置く。これにより、会話の原文に手順解説を混ぜず、作業記録だけを後から改善できる。

## 3. 会話の見た目は標準 Markdown で再構成
GitHub 上で会話の順序と読みやすさを保つため、ユーザーとGeminiの話者見出し、回答内の見出し、箇条書き、コードフェンス、区切り線を使う。色、余白、画面固有の操作ボタンは再現対象にしない。Markdown上では話者を見分けるためのラベルとして絵文字を使い、元画面のアイコン配置は再現しない。確認できない時刻は作り足さない。

## 4. 収録範囲は画面に表示された会話文
ユーザーとアシスタントの可視メッセージを順番に収録する。非表示の指示、内部の処理、ブラウザーや GitHub のツール出力は会話本文に入れない。ブラウザーで観察した事実は `progress.md` に別記する。これにより、読み手が会話内容と作業ログを区別できる。

## 5. 既存の空 README は上書きで更新
`gemini/neon/README.md` はサイズ 1 byte の既存ファイルだった。新規作成 API が 422 を返したため、同じ作成操作を繰り返さず、ファイル一覧から現在の blob SHA と本文を取得して更新 API を使った。既存ファイルの更新前に SHA を読む手順を今後も守る。

## 6. 小さなリモートコミットをチェックポイントとして使う
各ファイルやまとまりを作成・更新するたびに GitHub 上でコミットし、成功応答の commit SHA を進捗と状態に残す。リポジトリの Contents API が branch 上に直接コミットするため、独立した `git push` は発生しない。環境が失われてもリモートが作業の保存先になる。


## 7. 保存対象は現在開いていたGeminiの既存スレッド
初回は「この会話」をChatGPT側の会話と取り違え、クラウドブラウザーのGeminiは新規画面だと誤って記録した。ユーザーの訂正後に現在のタブを再確認し、Geminiの既存スレッド「トポス創発法」を対象と確定した。表示されていた9件のプロンプトと9件の回答を保存し、初回の誤ったconversation.mdは差し替えた。初回の判断は誤りの経緯としてprogress.mdに残し、現行の状態や手順として再利用しない。

## 8. 画面の本文はMarkdownに再構成し、セッションURLは残さない
Gemini画面で読めるアクセシビリティ表示をもとに、話者見出し、回答内見出し、箇条書き、コード例を再構成した。数式や装飾テキストが画面の読み取り上複数の断片に分かれる場合があるため、Markdownでは読みやすい表記に結合し、元画面と空白が完全一致するとは扱わない。アカウントに結び付く会話URLやIDは公開リポジトリへ記載しない。

## 9. Gemini側の会話状態を変更しない
今回の作業は既存スレッドを読むことに限り、新しいプロンプトを送信せず、Googleドキュメントへの書き出しも行わなかった。今後もユーザーが別途依頼しない限り、会話本文の保存に不要な外部操作を追加しない。
